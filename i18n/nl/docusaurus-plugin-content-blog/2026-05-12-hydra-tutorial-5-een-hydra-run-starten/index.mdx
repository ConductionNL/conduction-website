In de eerste vier delen ging het om concept, pipelines, gates en skills. Tijd om te draaien. Op je eigen machine draai je de stages van Hydra als containers: één stage tegelijk, of de hele keten tegen een wegwerp-repo. Een echte run op een echte app begint met een label, en de flows uit deel 7 nemen het daarna over. Dit deel behandelt beide, met de praktische valkuilen: credentials, de forge-instelling en images.

## Stap 1: clone en bekijk

```bash
git clone https://github.com/ConductionNL/hydra.git
cd hydra
cat CLAUDE.md
```

`CLAUDE.md` is de canonieke architectuur-doc. Goed om de eerste keer doorheen te scrollen. De map `secrets/` zit niet in git: `secrets/.env` maak je zelf aan in stap 3.

## Stap 2: credentials komen uit je omgeving

De lokale scripts van Hydra lezen precies twee credentials, en alleen uit omgevingsvariabelen:

```bash
export GH_TOKEN=$(gh auth token)        # forge-token; GIT_TOKEN werkt ook als alias
export CLAUDE_CODE_OAUTH_TOKEN=<token>  # uit `claude setup-token`; of ANTHROPIC_API_KEY=<key>
```

Er is geen credentials-bestand. `scripts/lib/env-credentials.sh` is de enige resolver, en die faalt dicht: ontbreekt een variabele, dan stopt het script met een reden, in plaats van een run te starten die drie seconden later sneuvelt op een 401. De scripts geven beide waarden aan de containers door op variabelenaam (`-e GH_TOKEN`), zodat de waarden nooit in de proceslijst of in een bestand terechtkomen.

<HexCard title="Je abonnement is van jou">
  Een Claude Max- of Pro-abonnement is persoonlijk: het mag je eigen werk draaien, niet dat van een organisatie. Lokaal regelt dat zichzelf, omdat het script onder jouw shell met jouw token draait. In de pijplijn weigeren de flows een stage waarvan de eigenaar niet vast te stellen is. Deel 7 legt uit hoe.
</HexCard>

:::note Oudere setups
Voor de overstap naar flows (2026) las Hydra `secrets/credentials.json`: een lijst Claude-tokens plus één git-token per persona, met automatische rotatie bij een rate-limit. Dat bestand, `scripts/lib/credentials.sh` en de rotatie zijn weg. Een achtergebleven `credentials.json` op schijf verandert niets.
:::

## Stap 3: `secrets/.env`

De **niet**-credential overrides. Anders voor productie dan voor je laptop.

```bash title="secrets/.env (lokaal werkstation)"
# Met welke forge de scripts en containers praten. Verplicht: er is geen default.
HYDRA_FORGE=github

# Welke images en tag te gebruiken. Lokaal bouw je vaak met -t localhost/hydra-*:test.
HYDRA_IMAGE_PREFIX=localhost/hydra
HYDRA_IMAGE_TAG=test

# Default review-scope (ADR-020): alleen PR-diff. Zet op 'full' alleen bij onboarding van een repo.
HYDRA_REVIEW_SCOPE=diff
```

`HYDRA_FORGE=github` is goed voor elke ConductionNL-repo; `forgejo` is alleen voor een klant die een eigen Forgejo draait. Er is geen default, omdat een forge raden betekent dat je je token naar een derde partij stuurt. Begin je vanaf `secrets/.env.example`, controleer dan die regel: oudere versies zetten hem op `codeberg`.

Tip: de image-defaults zijn `ghcr.io/conductionnl/hydra` als prefix en `latest` als tag. Laat `HYDRA_IMAGE_*` weg om de gepubliceerde images te gebruiken.

:::tip secrets/.env wordt automatisch geladen
`scripts/dev-run.sh` weigert te starten zonder dit bestand en laadt het zelf, net als `reconcile.sh` en de `cron-*.sh`-sweeps. Een tijd lang controleerde `dev-run.sh` alleen óf het bestand bestond en laadde het nooit, waardoor `HYDRA_FORGE=github` ingesteld leek terwijl elke container nog met Codeberg praatte ([hydra#391](https://github.com/ConductionNL/hydra/issues/391)). Elk entrypoint dat configuratie leest MOET dit bestand bij opstart sourcen; dat is een repo-breed contract.
:::

## Stap 4: build de container images

In CI pusht GitHub Actions alle images naar GHCR. Lokaal, met `HYDRA_IMAGE_PREFIX=localhost/hydra`, bouw je ze zelf:

```bash
# Base image: Nextcloud + PostgreSQL + OpenRegister (builder-dependency)
docker build -t ghcr.io/conductionnl/hydra-nextcloud-test:stable32 \
    -f images/nextcloud-test/Dockerfile .

# De drie pijplijn-images
docker build -t localhost/hydra-builder:test  -f images/builder/Dockerfile  .
docker build -t localhost/hydra-reviewer:test -f images/reviewer/Dockerfile .
docker build -t localhost/hydra-security:test -f images/security/Dockerfile .

# Eenmalig: het bridge-netwerk waarop de containers draaien
docker network create hydra-net
```

Controleer daarna met `docker images | grep hydra` dat de drie tags er staan. Reviewer en security zijn standalone (geen NC-dependency); de builder bouwt op de `hydra-nextcloud-test`-base.

## Stap 5: draai één stage met `dev-run.sh`

`dev-run.sh` start één container direct, zonder board en zonder flow eromheen. Zo zie je het snelst wat een persona doet:

```bash
# Builder: implementeer een OpenSpec-change op een branch en open een PR
./scripts/dev-run.sh openspec/changes/<change> builder \
    --repo-url https://github.com/ConductionNL/<app>

# Code review of security review op een bestaande PR
./scripts/dev-run.sh - reviewer --repo-url https://github.com/ConductionNL/<app> \
    --pr-url https://github.com/ConductionNL/<app>/pull/<N>
./scripts/dev-run.sh - security --repo-url https://github.com/ConductionNL/<app> \
    --pr-url https://github.com/ConductionNL/<app>/pull/<N>
```

De output van de persona verschijnt in je terminal, en zijn commits en comments komen op de PR.

## Stap 6: de hele keten op een wegwerp-repo

Wil je builder, reviewer en security na elkaar zien draaien, gebruik dan `smoke-test.sh`. Die werkt op een wegwerp-repo onder je eigen GitHub-account, dus aan een echte app wordt niets aangeraakt:

```bash
./scripts/smoke-test.sh --spec-dir /tmp/todo-mvp-spec \
    --github-user <jouw-github-user> --repo-name todo-app
```

Het script hernoemt een oudere `todo-app` naar `todo-app-runN`, maakt een verse aan met de spec erin, bouwt de images, draait de builder, daarna reviewer en security parallel, en print een samenvatting. De spec-map heeft een `design.md`, een `tasks.md` en een map `specs/` nodig. Vanuit Claude Code doet `/local-run` hetzelfde in één commando.

<HexCard title="Wat een lokale run níét bewijst">
  <code>dev-run.sh</code> en <code>smoke-test.sh</code> starten de containers direct, buiten elke flow. Ze schrijven <strong>geen run-record</strong>: geen stage-entry in <code>hydra.json</code>, geen eigenaar-attributie, geen label-state-machine. Een groene lokale keten laat zien dat de stages werken op deze spec. Over sequencing of attributie zegt hij niets. Daarvoor moet de run door de flows, zoals in stap 7.
</HexCard>

## Stap 7: een echte run op een doel-app

Op een echte app start je zelf geen containers. Je zet het trigger-label op het tracking-issue en de flows doen de rest:

- Het trigger-label `ready-to-build`.
- Optioneel `yolo`, als de PR mag auto-mergen zodra alles groen is.
- Optioneel `openspec` als je via OpenSpec werkt.

Via de Hydra-helper:

```bash
./scripts/hydra-label.sh ConductionNL/<app> <N> add ready-to-build
```

`scripts/hydra-label.sh` is het **preferred path**: het gebruikt de label-helpers uit `scripts/lib/labels.sh` en synct het GitHub Project board realtime. Een directe `gh issue edit --add-label` werkt ook, maar dan blijft het board in de oude kolom staan tot reconcile (elke 10 minuten) het oppikt.

De `hydra-dispatch`-flow vindt het label bij zijn volgende tik van vijf minuten en geeft het issue door aan `hydra-sequencer`. De definitie wordt geleverd met `enabled: false`, dus dit gebeurt alleen op een OpenRegister-instantie waar de flow aangezet is. Deel 7 behandelt die opzet.

<HexCard title="Wat is er met HYDRA_LABEL_PREFIX gebeurd?">
  Eerdere versies van dit deel besteedden een hele stap aan <code>HYDRA_LABEL_PREFIX</code>. Die gaf de lokale supervisor van elke developer een eigen label-namespace (<code>wilco-build:queued</code>), zodat twee supervisors op dezelfde repo elkaars werk niet oppakten. De supervisor is weg, en de flows zijn het enige dat nog werk oppakt. Die reageren alleen op de kale labels. De shell-tooling (<code>create-labels.sh --prefix</code>, <code>hydra-label.sh</code>, <code>reconcile.sh</code>) kent de variabele nog, maar geen enkele flow pakt een geprefixt label op. Laat hem leeg.
</HexCard>

## Stap 8: volg de pijplijn

Zodra de sequencer het issue heeft, gebeurt dit:

```
ready-to-build → build:queued → build:running → build:pass
              ↳ code-review:queued → :running → :pass / :fail
              ↳ security-review:queued → :running → :pass / :fail
              ↳ applier:queued → :running → :pass / :fail → done / needs-input
```

Je volgt het op twee plekken:

1. **GitHub issue**: de labels veranderen terwijl de sequencer de stages doorloopt.
2. **GitHub PR**: de commits van de builder en de inline comments van de reviewers.

Achter beide wordt elke stage vastgelegd in `openspec/changes/<slug>/hydra.json`, voordat het label verschuift. Deel 6 laat zien hoe je dat bestand leest. De flow-runs zelf leven in OpenRegister; er is geen logbestand op je machine om te tailen.

`yolo` gezet en alles groen? Dan zie je op het issue `done` verschijnen, op de PR een approve en een auto-merge. Geen `yolo`? Dan staat de PR klaar voor een mens om te mergen.

## Troubleshooting

<Troubleshooting title="Eerste-run problemen">
  <TroubleshootingItem symptom="Het script stopt meteen met een fout over een ontbrekende credential">
    Exporteer <code>GH_TOKEN</code> en <code>CLAUDE_CODE_OAUTH_TOKEN</code> (of <code>ANTHROPIC_API_KEY</code>) in dezelfde shell waarin je het script start. De resolver leest nooit een bestand, dus een <code>secrets/credentials.json</code> helpt niet.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="dev-run.sh meldt dat secrets/.env niet gevonden is">
    Maak het bestand uit stap 3 aan. Het moet in <code>secrets/</code> in de root van de hydra-repo staan, niet in je home-dir: de scripts lezen het via een vast pad relatief aan de repo-root.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Een container weigert te starten omdat HYDRA_FORGE niet gezet is">
    Zet <code>HYDRA_FORGE=github</code> in <code>secrets/.env</code>. De weigering is bewust: zonder die regel zou Hydra moeten raden waar je token heen moet.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Een stage gebruikt de ghcr.io-images terwijl ik lokaal heb gebouwd">
    Controleer dat <code>secrets/.env</code> daadwerkelijk <code>HYDRA_IMAGE_PREFIX=localhost/hydra</code> en <code>HYDRA_IMAGE_TAG=test</code> bevat, en dat de tags uit stap 4 overeenkomen.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Build start, geen image found error">
    <code>docker images | grep hydra-builder</code>. Geen treffer? Bouw eerst de base image (<code>hydra-nextcloud-test</code>) en daarna pas de builder. De builder-Dockerfile heeft de base als <code>FROM</code>. Een fout <code>network hydra-net not found</code> betekent dat je de laatste regel van stap 4 hebt overgeslagen.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Het label staat op het issue, maar er gebeurt niets">
    Niets op je machine let op labels. Op een echte app moet de <code>hydra-dispatch</code>-flow aangezet zijn in de OpenRegister-instantie (deel 7). Wil je lokaal een stage proberen, gebruik dan <code>dev-run.sh</code> uit stap 5.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Issue gaat direct naar needs-input zonder dat ik iets zie">
    Stale labels van een vorige run blijven hangen. Strip de oude stage-labels met <code>./scripts/hydra-label.sh ConductionNL/&lt;app&gt; &lt;N&gt; transition ready-to-build</code>. Dat zet het issue terug in een gedefinieerde starttoestand.
  </TroubleshootingItem>
</Troubleshooting>

<div className="tutorial-quiz">

**1. Waar halen de lokale scripts van Hydra hun credentials vandaan, en wat gebeurt er als er een ontbreekt?**

<Details summary="Hint">

Twee variabelen, één resolver. Valt die ergens op terug?

</Details>

<Details summary="Antwoord">

**Alleen uit de omgeving**: `GH_TOKEN` (of de alias `GIT_TOKEN`) voor de forge, en `CLAUDE_CODE_OAUTH_TOKEN` of `ANTHROPIC_API_KEY` voor het model. `scripts/lib/env-credentials.sh` faalt dicht: een ontbrekende variabele stopt het script met een expliciete reden en een exit-code die niet nul is. De resolver leest nooit een bestand, dus er is niets om op terug te vallen, en een verouderde `credentials.json` op schijf verandert niets.

</Details>

</div>

<div className="tutorial-quiz">

**2. Waarom heeft `HYDRA_FORGE` geen default?**

<Details summary="Hint">

Wat doet een script met je token zodra het besloten heeft met welke forge het praat?

</Details>

<Details summary="Antwoord">

Een forge raden betekent de credentials van de run naar een derde partij sturen. De default was vroeger `codeberg`, en zo is er ooit een GitHub-token bij codeberg.org terechtgekomen. Nu weigeren de scripts te starten tot je `github` (elke ConductionNL-repo) of `forgejo` (de eigen Forgejo van een klant) opgeeft.

</Details>

</div>

<div className="tutorial-quiz">

**3. Waarom roep je `./scripts/hydra-label.sh` aan in plaats van `gh issue edit --add-label` om een run te triggeren?**

<Details summary="Hint">

De labels zijn de bron van waarheid, maar er is nog iets dat ze moet volgen.

</Details>

<Details summary="Antwoord">

`hydra-label.sh` gaat via de label-helpers in `scripts/lib/labels.sh`, en elk daarvan eindigt met een sync van het GitHub Project board. Eén aanroep verandert dus het label én verplaatst de kaart. `gh issue edit` verandert alleen het label; het board blijft in de oude kolom tot `reconcile.sh` (elke 10 minuten) het verschil oppikt.

</Details>

</div>

<div className="tutorial-quiz">

**4. Je `smoke-test.sh`-keten kwam groen terug. Wat heb je bewezen, en wat niet?**

<Details summary="Hint">

Wat laat een run achter als er geen flow bij betrokken is?

</Details>

<Details summary="Antwoord">

**Bewezen:** de stages builder, reviewer en security werken op deze spec, met deze images en deze credentials.

**Niet bewezen:** iets over sequencing of attributie. `smoke-test.sh` en `dev-run.sh` starten containers direct, dus er wordt geen stage-record in `hydra.json` geschreven, geen eigenaar vastgelegd en geen label-state-machine doorlopen. Voor een claim als "de stage-records bewijzen het" heb je een run door de flows nodig.

</Details>

</div>
