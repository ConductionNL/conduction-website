In [part 5](/academy/hydra-tutorial-5-starting-a-run) you ran Hydra by hand: build the images, run a stage with `dev-run.sh`, label an issue. That is the right way to learn Hydra, but it is not how it runs day to day. In production nobody starts containers from a terminal. Instead a scheduled flow notices the labelled issue, and each stage starts from a pre-built image pulled from a registry. This part explains that path, and the three deployment models behind it.

## Same pipeline, different trigger

Nothing about the pipeline changes between local and CI. The personas, the labels, the gates, the no-loop rule from part 2: all identical. What changes is who pulls the trigger and where the work runs:

| | Local (part 5) | CI / production (this part) |
|---|---|---|
| Trigger | you run `dev-run.sh` or `smoke-test.sh` | the `hydra-dispatch` flow finds the label on its schedule |
| Where stages run | containers on your machine | the hermiq ExApp, started by OpenRegister flows |
| Images | you `docker build` them | pulled from GHCR (`ghcr.io/conductionnl/hydra-*`) |
| Credentials | `GH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` in your shell | a brokered credential id; the secret stays in the broker |

So everything you learned about labels and the state machine still applies. You are just handing the steering wheel to the flows.

## Trigger: flows, not Actions

Hydra's stage dispatch does not run in CI. It briefly did: [hydra#448](https://github.com/ConductionNL/hydra/pull/448) (2026-07-31) ran the stage as an Actions job, `hydra-stage.yml`, and [hydra#452](https://github.com/ConductionNL/hydra/pull/452) (2026-08-01) removed it again. (The older `hydra-build.yml` and `hydra-review.yml` had already been retired in May.) The people Hydra is built for have Nextcloud and LLM access on a Kubernetes environment someone else set up, and no forge account with Actions rights or cluster access of their own. So the stage now runs on what they already have: Nextcloud's job system, OpenRegister flows and the **hermiq ExApp**. Two flows in hydra's `flows/` folder, run by OpenRegister, decide what runs next:

- **`hydra-dispatch`** runs on a schedule (every five minutes), polls the forge for queued work and starts at most a fixed number of pipelines at once.
- **`hydra-sequencer`** moves an issue from stage to stage, and runs the dependency and sibling checks before it dispatches a spec. It searches the whole `ConductionNL` organisation in one call rather than walking the repos one by one.

What GitHub Actions still does is build the images, in **`.github/workflows/hydra-image.yml`**, on every push to `main` or `development`. Nothing else can build a container image, so that is the one CI job left.

The entry point is unchanged from part 1: a label on the tracking issue, not a person at a terminal. Same contract, different plumbing.

<HexCard title="GitHub for Conduction, Forgejo for customer instances">
  Hydra is built forge-agnostic. The <code>HYDRA_FORGE</code> variable selects the REST adapter: <code>github</code> (<code>scripts/lib/github-rest.sh</code>) for every ConductionNL repo, or <code>forgejo</code> (<code>codeberg</code> is accepted as an alias, <code>scripts/lib/forgejo-rest.sh</code>) for a customer who runs a self-hosted Forgejo. There is <strong>no default</strong>: <code>scripts/lib/forge-api.sh</code> refuses to start when the variable is unset, because guessing a forge means sending the run's credentials to a third party. It used to default to <code>codeberg</code>, and that is how a GitHub token once ended up at codeberg.org. If older docs show <code>codeberg.org/Conduction/&lt;app&gt;</code> URLs, that is the 2026-05-29 move to Codeberg showing. It was reversed (directive 2026-07-17, executed 2026-07-23), and GitHub is the only host for ConductionNL work.
</HexCard>

## Images: the GitHub Container Registry

In a local run you build the images yourself (part 5). For unattended runs that would waste minutes on every stage, so `hydra-image.yml` builds them once and pushes them to the **GitHub Container Registry** (GHCR): the `hydra-nextcloud-test:stable32` base image first, `hydra-builder` on top of it, and `hydra-reviewer` and `hydra-security` alongside. The naming is driven by two variables in `secrets/.env`:

```bash
# production values; part 5 used localhost/hydra and test for local builds
HYDRA_IMAGE_PREFIX=ghcr.io/conductionnl/hydra
HYDRA_IMAGE_TAG=latest
```

So the reviewer image resolves to `ghcr.io/conductionnl/hydra-reviewer:latest`, and the same for builder and security. (The applier image is not built by this workflow.) `latest` only moves when a release is published. Every push to `main` or `development` also publishes an immutable `sha-<short>` tag, and pinning `HYDRA_IMAGE_TAG` to one of those is how you freeze a known-good pipeline version instead of always tracking `latest`.

## Credentials: a reference, not a token

Production Hydra never uses a shared org-admin token, and it never holds a forge token at all. Every forge call the flows make, whether for an issue, a label, a comment or a pull request, goes through one OpenConnector source, `flows/hydra-forge.source.json`. That source carries only a `credentialRef`: the id of a credential that lives in the broker (Doriath). The broker fills in the secret and sends the call, locked to `api.github.com`. What hydra stores is a uuid:

```json
"authentication": {
  "credentialRef": { "credentialId": "{brokeredGithubCredentialId}" }
}
```

When the reference cannot be resolved, the run is refused. Nothing falls back to another token.

The Claude side follows the personal-scope rule from part 5:

1. **Every run has an owner.** It is resolved once per cycle: the issue's `owner:<uid>` marker, or else the person who applied the label. A bot is never the owner.
2. **A subscription only serves its owner.** A Claude Max or Pro credential runs only its owner's stages. A run without a resolvable owner may only be served by an organisation API key. The workload step refuses a stage it cannot attribute, and `hydra-record-stage` writes no record without a `credential_owner`, so an unattributed stage can never advance its label.

`hydra.json` records whose credential ran each stage (`cycles[].owner`, `stages[].credential_owner`). It never holds the token itself.

:::note What changed
Until 2026 this section described `secrets/credentials.json`: a list of Claude tokens with automatic rotation on rate-limit, plus one git token per persona. The file, the token pool and the rotation were retired with the move to flows.
:::

## The three deployment models

Hydra's `docs/deployment-models.md` describes three ways to run it, in increasing operational weight.

<HexCard title="Model 1: local (developer machine)">
  Build the images, run one stage with <code>dev-run.sh</code> or the whole chain with <code>smoke-test.sh</code>. This is part 5 of this series. Best for development and debugging. Fully documented. It writes no run record, so it shows that the stages work, not that the pipeline does.
</HexCard>

<HexCard title="Model 2: GitHub Actions (images only since August 2026)">
  Until hydra#452 (2026-08-01) the build and review stages ran as Actions jobs, triggered by issue labels and PR events, with credentials in org secrets. That dispatch was removed: the stage now runs in the hermiq ExApp, started by the OpenRegister flows above. What stays in GitHub Actions is the image build, <code>hydra-image.yml</code>, which every other model pulls from.
</HexCard>

<HexCard title="Model 3: Kubernetes and ArgoCD">
  Each stage runs as a Kubernetes <code>Job</code> (<code>manifests/builder-job.yaml</code>, <code>reviewer-job.yaml</code>, <code>security-job.yaml</code>), with a <code>NetworkPolicy</code> and an ArgoCD <code>Application</code> that syncs <code>manifests/</code> from <code>main</code>. For scale and isolation.
</HexCard>

<HexCard title="Honest status: Model 3 is infrastructure-as-code, not a runbook">
  The Kubernetes manifests exist and are real. But at the time of writing there is no step-by-step operator guide for the K8s path: no documented credential-setup-for-cluster, no runbook. If you are standing up Model 3, treat the manifests as the source of truth and expect to read them directly rather than follow a playbook. This tutorial will not pretend a guide exists that does not. Model 1 and the image build are the well-trodden paths.
</HexCard>

## Troubleshooting CI runs

<Troubleshooting title="Common CI-specific snags">
  <TroubleshootingItem title="The label is set but no stage starts">
    Unattended dispatch is the <code>hydra-dispatch</code> flow, not an Actions workflow, so there is no workflow run to look for. Its definition ships with <code>enabled: false</code>: check that the flow is activated on the OpenRegister instance, then give it one five-minute tick.
  </TroubleshootingItem>
  <TroubleshootingItem title="A stage fails pulling its image">
    The tag is wrong or the image was never built. Confirm <code>hydra-image.yml</code> ran on GitHub Actions and pushed <code>ghcr.io/conductionnl/hydra-&lt;role&gt;</code> with the expected tag, and that the host has pull access to GHCR. A <code>codeberg.org/conduction/hydra-*</code> reference is stale configuration: no Hydra image was ever published there.
  </TroubleshootingItem>
  <TroubleshootingItem title="A stage is refused as unattributed">
    The run has no owner that can be resolved. Put an <code>owner:&lt;uid&gt;</code> marker on the issue, or have a person (not a bot) apply the label. Only an organisation API key may run a stage without an owner.
  </TroubleshootingItem>
  <TroubleshootingItem title="Every forge call fails with a credential error">
    The <code>credentialId</code> in <code>hydra-forge.source.json</code> is instance-specific. When you apply the source, substitute the id of the credential in your own OpenRegister instance.
  </TroubleshootingItem>
</Troubleshooting>

## Test yourself

<div className="tutorial-quiz">

**1. What actually changes between a local run (part 5) and a CI run, and what stays the same?**

<Details summary="Hint">

Think about the trigger and the runtime versus the pipeline itself.

</Details>

<Details summary="Answer">

What changes: the trigger (the scheduled `hydra-dispatch` flow finding the label instead of you starting a container), where stages run (the hermiq ExApp instead of containers on your machine), where images come from (a GHCR pull instead of a local `docker build`), and where credentials live (a brokered credential id instead of variables in your shell).

What stays the same: the entire pipeline. Personas, labels, the state machine, the 22 gates, the no-loop rule. The contract is still one tracking issue labelled `ready-to-build`.

</Details>

</div>

<div className="tutorial-quiz">

**2. Why does the forge source hold a credential id instead of a token?**

<Details summary="Hint">

Where can a secret leak from if it is never in hydra's files at all?

</Details>

<Details summary="Answer">

The secret never leaves the broker. Hydra's flows, config and logs hold only a uuid, so there is no token in them to leak. The broker refuses an authentication block that holds anything next to the reference, because a secret embedded beside the reference is exactly what the reference exists to prevent. And when the id cannot be resolved, the run is refused instead of falling back to some other token. A shared org-admin token stays explicitly forbidden.

</Details>

</div>

<div className="tutorial-quiz">

**3. Which deployment model no longer runs pipeline stages, and which one lacks a written operator runbook?**

<Details summary="Hint">

One lost its stage dispatch in August 2026. One runs on Kubernetes.

</Details>

<Details summary="Answer">

Model 2 (GitHub Actions) has not run stages since hydra#452 (2026-08-01); it only builds the images. Model 3 (Kubernetes and ArgoCD) has real manifests but no step-by-step operator runbook yet, so you read the manifests directly. Model 1 (local) is parts 5 and 6.

</Details>

</div>
