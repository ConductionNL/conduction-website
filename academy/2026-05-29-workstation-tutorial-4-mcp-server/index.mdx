A workstation isn't really complete until at least one MCP server is wired into your project root via `.mcp.json`. This part covers the basics and gets you a working Playwright browser pool. The dedicated **Conduction MCP server** install lives in its own tutorial — we link to it at the bottom.

## In one sentence

MCP is a small open protocol that lets Claude Code call **out** to external services via a uniform interface. An "MCP server" is any program that speaks that protocol; Claude treats it as a tool provider. You wire servers into a project by listing them in `.mcp.json` at the project root.

A few servers you'll meet at Conduction:

- **`browser-1` … `browser-7`** — Playwright browser instances Claude can use for testing skills (`/test-app`, `/test-counsel`, the `hydra-gate-*` family).
- **The Conduction MCP server** — live access to internal Conduction systems while you work. Covered in its own tutorial.
- **Nextcloud MCP** — direct access to a running Nextcloud instance from Claude. Optional.

This module deliberately stops at the Playwright pool: it's the one every Conduction developer needs and it works without any extra accounts.

## Step 1: create `.mcp.json` at the project root

In a Conduction project, the file already exists — open it, scroll, confirm. In a fresh folder, create it. The minimum configuration that all testing skills assume is the **seven-browser pool**: six headless browsers for parallel agents, one headed browser for when you want to watch.

`/path/to/your-project/.mcp.json`:

```json
{
  "mcpServers": {
    "browser-1": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    },
    "browser-2": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    },
    "browser-3": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    },
    "browser-4": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    },
    "browser-5": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    },
    "browser-6": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--isolated"]
    },
    "browser-7": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--browser", "chromium", "--headless", "--isolated"]
    }
  }
}
```

Notice the asymmetry: **browser-6 omits `--headless`**. That's deliberate — it's the visible browser for when you want to watch Claude work. The other six stay invisible.

> **No need to type this from scratch.** The `.github` repo ships an [example .mcp.json](https://github.com/ConductionNL/.github/blob/main/docs/claude/examples/.mcp.json.example) you can copy directly.

## Step 2: trust the servers via `.claude/settings.json`

Every Conduction repo ships a `.claude/settings.json` (project-level — separate from your global one) that pre-approves the MCP servers so background agents don't get blocked by prompts. The two relevant lines:

```json
{
  "enableAllProjectMcpServers": true,
  "permissions": {
    "allow": ["mcp__browser-*"]
  }
}
```

- **`enableAllProjectMcpServers: true`** — auto-approves all servers listed in `.mcp.json` without a per-reload prompt.
- **`mcp__browser-*`** — pre-approves every browser tool call so sub-agents working in parallel don't get silently denied.

In a fresh folder, create these settings yourself. In a Conduction repo, they're already there.

## Step 3: reload VS Code

`Ctrl+Shift+P` → **"Developer: Reload Window"**. VS Code re-reads `.mcp.json` and starts the browser processes.

## Step 4: verify

Open the MCP servers panel in VS Code. Two equivalent ways:

- Type **`/MCP servers`** in the Claude Code chat input, or
- `Ctrl+Shift+P` → search **"MCP servers"** → open the panel.

All seven browsers should show **Connected**. If any show an error, open the output panel: `Ctrl+Shift+P` → **"Output: Focus on Output"** → select **Claude VSCode** from the dropdown — the error line spells out what went wrong.

> **Common cause if a browser fails to connect:** the Playwright Chromium binary isn't installed. Run `npx playwright install chromium` from your WSL terminal (you should already have this from Part 2 Step 9). Reload the window after.

## How does Claude know which browser to use?

There's no central dispatcher. The skills themselves assign browsers — by convention:

| Browser | When it's used |
| --- | --- |
| `browser-1` | The default; your main session uses this. |
| `browser-2`…`browser-5` and `browser-7` | Parallel sub-agents (e.g. `/test-app` Full mode, `/test-counsel`). |
| `browser-6` (**headed**) | When you've explicitly asked Claude to "show me" — that window pops up so you can watch. |

If a browser errors out, Claude falls back to the next numbered one. You don't have to manage this manually.

## Why seven browsers?

A pragmatic choice from a few years of internal testing:

- One default + five parallel sub-agents = six headless. That covers the heaviest parallel scenario in `/test-app` Full mode (five concurrent sub-agents plus the orchestrator).
- One headed browser for observation — handy when you want to *see* what Claude is doing rather than just read the result.

Other workspaces may use fewer (or more) browsers depending on parallelism. The Nextcloud workspace uses these seven; for a one-off prototype you can drop to two and be fine.

## What about the Conduction MCP server?

For Conduction projects, the Playwright pool alone isn't enough. The **Conduction MCP server** — a server we run internally — gives Claude live access to the systems we build with: registers, catalogs, the Hydra job board, and more.

It's a separate install with its own auth and configuration. We split it out into a dedicated tutorial so this one stays short:

- **Tutorial (planned):** [Set up the Conduction MCP server](https://github.com/ConductionNL/.github/issues/55) — see issue #55 for status.

When that tutorial is live, you'll add another entry to the same `.mcp.json` and reload. The Playwright pool stays.

## A note on `.mcp.json` vs. `~/.claude/settings.json`

Two files, different scopes. Keep them straight:

| File | Scope | What it does |
| --- | --- | --- |
| `~/.claude/settings.json` | **User-level**, all projects | Your safety policy, write-approval hooks, version check (Part 3). |
| `<project>/.mcp.json` | **Project-level**, this repo | Which MCP servers to launch for this project. Browsers, the Conduction MCP server, anything else specific. |
| `<project>/.claude/settings.json` | **Project-level**, this repo | Project permissions, MCP allowlist, pre-approvals. |

The user-level config never lists MCP servers; the project-level config does. That separation means each project picks its own set of servers without touching your global safety policy.

    VS Code didn't pick up <code>.mcp.json</code>. Reload the window (<code>Ctrl+Shift+P</code> → Developer: Reload Window). If still empty, confirm the file is at the project root and is valid JSON — paste it into <a href="https://jsonlint.com">jsonlint.com</a>.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="One specific browser errors with 'browserType.launchPersistentContext: Executable doesn't exist'">
    The Playwright Chromium binary isn't installed. Run <code>npx playwright install chromium</code> from your WSL terminal, then reload VS Code.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="A background agent says 'tool call denied' for mcp__browser-3">
    The project's <code>.claude/settings.json</code> doesn't have the <code>mcp__browser-*</code> allow rule, or <code>enableAllProjectMcpServers</code> is missing. Add both, reload, retry.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="browser-6 starts headless even though I removed --headless">
    Check there's no <code>HEADLESS=true</code> in your shell environment, and that no other <code>--headless</code> flag was added by an extension config. Reload and watch the output panel during startup to confirm the args passed in.
  </TroubleshootingItem>

**1. What does MCP stand for, and what's its job inside Claude Code?**

<Details summary="Hint">

Three letters. The middle word is what every external tool Claude touches needs to share.

</Details>

<Details summary="Answer">

**Model Context Protocol.** It's the small open protocol that lets Claude Code call out to external services — browsers, Slack, GitHub, your local Nextcloud, the Conduction MCP server — through a uniform interface.

Anything that speaks MCP can be wired into a project's `.mcp.json` and Claude can use it as a tool. Without MCP, every external integration would need a custom adapter; with MCP, they all look the same to Claude.

</Details>

**2. Why does the default Conduction pool have *seven* browsers, and why is one of them headed?**

<Details summary="Hint">

Six headless covers a specific parallel scenario; the seventh has a different purpose.

</Details>

<Details summary="Answer">

**Six headless browsers** cover the heaviest parallel scenario in `/test-app` Full mode: one orchestrator session plus five concurrent sub-agents, each on its own browser, plus one spare (`browser-7`). The Hydra pipeline and `/test-counsel` lean on the same pool.

**The seventh browser is headed** (`browser-6` — note: numbered, not the last) because sometimes you want to *see* what Claude is doing rather than just read the result. When you ask Claude to "show me" or "watch", it switches to that visible window. Otherwise all real work happens on the headless six.

</Details>

**3. Which two project-level settings pre-approve the MCP browsers so background agents aren't blocked by prompts?**

<Details summary="Hint">

One is a boolean that auto-trusts every server in `.mcp.json`; the other is a pattern in the permissions allowlist.

</Details>

<Details summary="Answer">

In the project's `.claude/settings.json`:

```json
{
  "enableAllProjectMcpServers": true,
  "permissions": {
    "allow": ["mcp__browser-*"]
```

<div className="tutorial-quiz">

**4. Where does `.mcp.json` live, and what's the difference between it and `~/.claude/settings.json`?**

<Details summary="Hint">

Two files, two scopes. One is per-user, one is per-project.

</Details>

<Details summary="Answer">

`.mcp.json` lives at the **project root** (next to `package.json` or `composer.json`). It's per-project: which MCP servers should this project launch — browsers, the Conduction MCP server, anything else.

`~/.claude/settings.json` is **user-level**: your safety policy, write-approval hooks, version check. It applies to every project you open and never lists MCP servers itself.

The split matters because it lets each project pick its own MCP servers without touching your global safety configuration. Updating one never changes the other.

</Details>
