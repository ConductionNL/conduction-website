## Skills, in één alinea

Een **skill** in Claude Code is een mapje met een `SKILL.md` (en optioneel scripts, `examples/`, helpers). Het mapje hangt onder `.claude/skills/<naam>/`. Claude leest de skill in zijn context wanneer hij relevant is — soms expliciet aangeroepen via een slash-command (`/opsx-apply`), soms automatisch geactiveerd op basis van de skill-omschrijving en de huidige situatie.

Voor Hydra zijn skills de **bundel-eenheid van gedrag**: in plaats van duizend regels prompt-tekst direct in een persona's `CLAUDE.md` te plakken, zit het in een skill, hergebruikbaar en testbaar.

## Drie skill-families binnen Hydra

Hydra's `hydra/.claude/skills/` bevat zo'n 50 skills, ongeveer drie families:

### Familie 1: OpenSpec workflow (`opsx-*`)

De OPSX-skills implementeren de Conduction-workflow voor OpenSpec-changes. Voorbeelden:

- `opsx-new` — start een nieuwe change (proposal scaffold, schema-keuze).
- `opsx-ff` — "fast-forward": maakt de change + alle artefacten (design, tasks, specs) klaar voor implementatie in één pass.
- `opsx-plan-to-issues` — converteert `tasks.md` naar een tracking-issue.
- `opsx-apply` — implementeert taken uit een change (de builder gebruikt dit, of een mens).
- `opsx-verify` — controleert dat de implementatie de change-artefacten dekt vóór archief.
- `opsx-archive` — archiveert een afgeronde change, syncing delta naar de spec.
- `opsx-continue` — pak een onderbroken change op waar je gebleven bent.
- `opsx-reverse-spec` — reverse-engineert een spec uit bestaande code (Bucket 2 cluster).
- `opsx-annotate` — past `@spec` PHPDoc-tags toe na een coverage-scan (Bucket 1).
- `opsx-coverage-scan` — audit een legacy app op spec ↔ code coverage.

De Builder (Al Gorithm) heeft de hele OPSX-suite ingebakken in zijn Docker image. Zijn standaard run is in feite: lees context, run `opsx-apply`, run quality, klaar.

### Familie 2: Quality + security gates (`hydra-gate-*`)

Deze zag je al in deel 3 — `hydra-gate-spdx`, `hydra-gate-forbidden-patterns`, en de rest. Elke gate is een skill die één deterministische check beschrijft + uitvoert. De reviewers (Juan Claude en Clyde) hebben deze gates expliciet als "mandatory block" in hun review-checklist; de builder kent ze als anti-patronen die hij moet vermijden.

De parent-skill `hydra-gates` is een dispatcher: hij wordt aangeroepen door de reviewer en activeert vervolgens elke individuele gate.

### Familie 3: Team-rollen (`team-*`)

Skills die een specifiek soort werk modelleren via een persona-frame:

- `team-po` (Product Owner) — schrijft user stories en acceptatiecriteria.
- `team-sm` (Scrum Master) — beheert backlog en sprint-planning artefacten.
- `team-architect` — neemt architectuurbeslissingen, schrijft ADR-drafts.
- `team-backend` — implementeert backend-werk (PHP, services, mappers).
- `team-frontend` — implementeert frontend-werk (Vue 2, Pinia, NL Design System).
- `team-reviewer` — een handmatige variant van het reviewer-werk.
- `team-qa` — schrijft testcases en testplannen.

Deze skills worden zelden in de pipeline gebruikt; ze zijn gericht op de **mens** die naast Hydra in een terminal werkt en even één rol wil invullen.

## Skill versus slash-command

Beide zijn manieren om Claude een bundel gedrag te laten oppakken. Het verschil:

| | Skill | Slash-command |
|---|---|---|
| **Bestand** | `.claude/skills/<naam>/SKILL.md` | `.claude/commands/<naam>.md` |
| **Activering** | Vaak automatisch op basis van context | Altijd handmatig: <code>/<naam></code> |
| **Persistentie** | Beschikbaar zolang Claude in de juiste cwd zit | Per-conversatie |
| **Wie gebruikt 'em** | Vooral de pipeline-personas | Vooral mensen op de CLI |

Er bestaat overlap: veel OPSX-functionaliteit is **zowel** als skill als als slash-command beschikbaar. `/opsx-apply` is de slash-command voor mensen; de Builder-container heeft dezelfde skill ingebakken en roept hem programmatic aan.

## Wat er allemaal beschikbaar is

In een fris Hydra-checkout kun je dit zien:

```bash
ls hydra/.claude/skills/
# een lange lijst — opsx-*, hydra-gate-*, team-*, test-*, review-pr, journeydoc-*, ...
```

Daarnaast heeft Hydra zogenaamde **vendor skills** onder `hydra/vendor/skills/`:

- `code-review` — een communautaire review-skill van Anthropic.
- `trailofbits` — security-patronen van Trail of Bits.
- `owasp` — OWASP-top-10-checklists.

Die laatste drie laden we in bij Juan en Clyde om hen extra dekking te geven boven op onze eigen `hydra-gate-*` skills.

## Wanneer schrijf je een nieuwe skill?

De pragmatische test: schrijf een skill als…

1. **De check / het gedrag is herhaalbaar** — meer dan eens nodig, op meer dan één plek.
2. **Het is mechanisch beschrijfbaar** — je kunt het in 1-3 alinea's instrueren, zonder dat het ontaardt in "het hangt van de context af".
3. **Een persona of een mens zou er baat bij hebben.** Geen skill schrijven omdat het kan.

Voor een fout-positieve gate (deel 3): je past de bestaande skill aan, je schrijft geen nieuwe. Voor een nieuw klasse-fout dat je 3x ziet langskomen: ja, daar verdient het een eigen `hydra-gate-*` skill.

  Hydra heeft een ingebouwde <code>/skill-creator</code> slash-command die je door het maken van een nieuwe skill leidt: scaffold, frontmatter, eval-harness, performance-meting.
