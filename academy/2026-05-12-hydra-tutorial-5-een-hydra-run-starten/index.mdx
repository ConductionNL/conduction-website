The first four parts were about concept, pipelines, gates and skills. Time to actually run. On your own machine you run Hydra's stages as containers: one stage at a time, or the whole chain against a throwaway repo. A real run on a real app starts with a label, and the flows from part 7 carry it from there. This part covers both, with the practical pitfalls: credentials, the forge setting, and images.

## Step 1: clone and look around

```bash
git clone https://github.com/ConductionNL/hydra.git
cd hydra
cat CLAUDE.md
```

`CLAUDE.md` is the canonical architecture doc. Worth scrolling through the first time. The `secrets/` folder is not in git: you create `secrets/.env` yourself in step 3.

## Step 2: credentials come from your environment

Hydra's local scripts read exactly two credentials, and only from environment variables:

```bash
export GH_TOKEN=$(gh auth token)        # forge token; GIT_TOKEN is accepted as an alias
export CLAUDE_CODE_OAUTH_TOKEN=<token>  # from `claude setup-token`; or ANTHROPIC_API_KEY=<key>
```

There is no credentials file. `scripts/lib/env-credentials.sh` is the one resolver, and it fails closed: when a variable is missing, the script stops with a reason instead of starting a run that dies three seconds later with a 401. The scripts pass both values to the containers by variable name (`-e GH_TOKEN`), so the values never end up in the process list or in a file.

<HexCard title="Your subscription is yours">
  A Claude Max or Pro subscription is personal-scope: it may run your own work, not an organisation's. Locally that takes care of itself, because the script runs under your shell with your token. In the pipeline, the flows refuse to run a stage whose owner cannot be established. Part 7 explains how.
</HexCard>

:::note Older setups
Before the move to flows (2026), Hydra read `secrets/credentials.json`: a list of Claude tokens plus one git token per persona, with automatic rotation on rate-limit. That file, `scripts/lib/credentials.sh` and the rotation are gone. A leftover `credentials.json` on disk changes nothing.
:::

## Step 3: `secrets/.env`

The **non**-credential overrides. Different for production than for your laptop.

```bash title="secrets/.env (local workstation)"
# Which forge the scripts and containers talk to. Required: there is no default.
HYDRA_FORGE=github

# Which images and tag to use. Locally you often build with -t localhost/hydra-*:test.
HYDRA_IMAGE_PREFIX=localhost/hydra
HYDRA_IMAGE_TAG=test

# Default review scope (ADR-020): PR diff only. Set to 'full' only when onboarding a repo.
HYDRA_REVIEW_SCOPE=diff
```

`HYDRA_FORGE=github` is right for every ConductionNL repo; `forgejo` is only for a customer who runs a self-hosted Forgejo. It has no default because guessing a forge means sending your token to a third party. If you start from `secrets/.env.example`, check that line: older copies set it to `codeberg`.

Tip: the image defaults are `ghcr.io/conductionnl/hydra` as prefix and `latest` as tag. Leave `HYDRA_IMAGE_*` out to use the published images.

:::tip secrets/.env is loaded automatically
`scripts/dev-run.sh` refuses to start without this file and loads it itself, and so do `reconcile.sh` and the `cron-*.sh` sweeps. For a while `dev-run.sh` only checked that the file existed and never loaded it, so `HYDRA_FORGE=github` looked configured while every container still talked to Codeberg ([hydra#391](https://github.com/ConductionNL/hydra/issues/391)). Every entrypoint that reads configuration MUST source this file at startup; that's a repo-wide contract.
:::

## Step 4: build the container images

In CI, GitHub Actions pushes all images to GHCR. Locally, with `HYDRA_IMAGE_PREFIX=localhost/hydra` set, you build them yourself:

```bash
# Base image: Nextcloud + PostgreSQL + OpenRegister (builder dependency)
docker build -t ghcr.io/conductionnl/hydra-nextcloud-test:stable32 \
    -f images/nextcloud-test/Dockerfile .

# The three pipeline images
docker build -t localhost/hydra-builder:test  -f images/builder/Dockerfile  .
docker build -t localhost/hydra-reviewer:test -f images/reviewer/Dockerfile .
docker build -t localhost/hydra-security:test -f images/security/Dockerfile .

# Once: the bridge network the containers run on
docker network create hydra-net
```

Then check with `docker images | grep hydra` that the three tags are there. Reviewer and security are standalone (no NC dependency); the builder builds on the `hydra-nextcloud-test` base.

## Step 5: run one stage with `dev-run.sh`

`dev-run.sh` starts one container directly, with no board and no flow around it. That is the quickest way to see what a persona does:

```bash
# Builder: implement an OpenSpec change on a branch and open a PR
./scripts/dev-run.sh openspec/changes/<change> builder \
    --repo-url https://github.com/ConductionNL/<app>

# Code review or security review on an existing PR
./scripts/dev-run.sh - reviewer --repo-url https://github.com/ConductionNL/<app> \
    --pr-url https://github.com/ConductionNL/<app>/pull/<N>
./scripts/dev-run.sh - security --repo-url https://github.com/ConductionNL/<app> \
    --pr-url https://github.com/ConductionNL/<app>/pull/<N>
```

The persona's output streams to your terminal, and its commits and comments land on the PR.

## Step 6: the whole chain on a throwaway repo

To see builder, reviewer and security run back to back, use `smoke-test.sh`. It works on a disposable repo under your own GitHub account, so nothing on a real app is touched:

```bash
./scripts/smoke-test.sh --spec-dir /tmp/todo-mvp-spec \
    --github-user <your-github-user> --repo-name todo-app
```

The script renames an older `todo-app` to `todo-app-runN`, creates a fresh one with the spec uploaded, builds the images, runs the builder, then runs reviewer and security in parallel, and prints a summary. The spec directory needs a `design.md`, a `tasks.md` and a `specs/` folder. From Claude Code, `/local-run` does the same in one command.

<HexCard title="What a local run does not prove">
  <code>dev-run.sh</code> and <code>smoke-test.sh</code> start the containers directly, outside any flow. They write <strong>no run record</strong>: no stage entry in <code>hydra.json</code>, no owner attribution, no label state machine. A green local chain shows that the stages work on this spec. It says nothing about sequencing or attribution. For that the run has to go through the flows, as in step 7.
</HexCard>

## Step 7: a real run on a target app

On a real app you don't start containers yourself. You put the trigger label on the tracking issue and the flows do the rest:

- The trigger label `ready-to-build`.
- Optionally `yolo`, if the PR may auto-merge once everything is green.
- Optionally `openspec` if you're working via OpenSpec.

Via the Hydra helper:

```bash
./scripts/hydra-label.sh ConductionNL/<app> <N> add ready-to-build
```

`scripts/hydra-label.sh` is the **preferred path**: it uses the label helpers from `scripts/lib/labels.sh` and syncs the GitHub Project board in real time. A direct `gh issue edit --add-label` works too, but then the board stays in the old column until reconcile (every 10 minutes) picks it up.

The `hydra-dispatch` flow finds the label on its next five-minute tick and hands the issue to `hydra-sequencer`. Its definition ships with `enabled: false`, so this only happens on an OpenRegister instance where the flow has been switched on. Part 7 covers that setup.

<HexCard title="What happened to HYDRA_LABEL_PREFIX?">
  Earlier versions of this part spent a whole step on <code>HYDRA_LABEL_PREFIX</code>. It gave each developer's local supervisor its own label namespace (<code>wilco-build:queued</code>), so two supervisors watching the same repo did not pick up each other's work. The supervisor is gone, and the flows are the only thing left that picks up work. They act on the bare labels only. The shell tooling (<code>create-labels.sh --prefix</code>, <code>hydra-label.sh</code>, <code>reconcile.sh</code>) still understands the variable, but no flow picks up a prefixed label. Leave it unset.
</HexCard>

## Step 8: follow the pipeline

Once the sequencer has the issue, this happens:

```
ready-to-build → build:queued → build:running → build:pass
              ↳ code-review:queued → :running → :pass / :fail
              ↳ security-review:queued → :running → :pass / :fail
              ↳ applier:queued → :running → :pass / :fail → done / needs-input
```

You follow it in two places:

1. **GitHub issue**: the labels change as the sequencer advances the stages.
2. **GitHub PR**: the builder's commits and the reviewers' inline comments.

Behind both, every stage is recorded in `openspec/changes/<slug>/hydra.json` before its label moves. Part 6 shows how to read that file. The flow runs themselves live in OpenRegister; there is no log file on your machine to tail.

Set `yolo` and is everything green? Then you'll see `done` appear on the issue, an approval on the PR, and an auto-merge. No `yolo`? Then the PR is ready for a human to merge.

## Troubleshooting

<Troubleshooting title="First-run problems">
  <TroubleshootingItem symptom="The script stops straight away with a missing-credential error">
    Export <code>GH_TOKEN</code> and <code>CLAUDE_CODE_OAUTH_TOKEN</code> (or <code>ANTHROPIC_API_KEY</code>) in the same shell you start the script from. The resolver never reads a file, so a <code>secrets/credentials.json</code> does not help.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="dev-run.sh says secrets/.env not found">
    Create the file from step 3. It has to be in <code>secrets/</code> at the root of the hydra repo, not in your home dir: the scripts read it from a fixed path relative to the repo root.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="A container refuses to start because HYDRA_FORGE is unset">
    Add <code>HYDRA_FORGE=github</code> to <code>secrets/.env</code>. The refusal is deliberate: without it, Hydra would have to guess where to send your token.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="A stage uses the ghcr.io images even though I built locally">
    Check that <code>secrets/.env</code> actually contains <code>HYDRA_IMAGE_PREFIX=localhost/hydra</code> and <code>HYDRA_IMAGE_TAG=test</code>, and that the tags from step 4 match.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Build starts, no image found error">
    <code>docker images | grep hydra-builder</code>. No hit? Build the base image first (<code>hydra-nextcloud-test</code>) and then the builder. The builder Dockerfile has the base as <code>FROM</code>. A <code>network hydra-net not found</code> error means you skipped the last line of step 4.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="The label is on the issue, but nothing happens">
    Nothing on your machine watches labels. On a real app the <code>hydra-dispatch</code> flow has to be switched on in the OpenRegister instance (part 7). To try a stage locally, use <code>dev-run.sh</code> from step 5 instead.
  </TroubleshootingItem>
  <TroubleshootingItem symptom="Issue jumps straight to needs-input without me seeing anything">
    Stale labels from a previous run are still hanging around. Strip the old stage labels with <code>./scripts/hydra-label.sh ConductionNL/&lt;app&gt; &lt;N&gt; transition ready-to-build</code>. That puts the issue back into a defined starting state.
  </TroubleshootingItem>
</Troubleshooting>

<div className="tutorial-quiz">

**1. Where do Hydra's local scripts get their credentials, and what happens when one is missing?**

<Details summary="Hint">

Two variables, one resolver. Does it fall back to anything?

</Details>

<Details summary="Answer">

From the **environment only**: `GH_TOKEN` (or its alias `GIT_TOKEN`) for the forge, and `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` for the model. `scripts/lib/env-credentials.sh` fails closed: a missing variable stops the script with an explicit reason and a non-zero exit. It never reads a file, so there is nothing to fall back to, and a stale `credentials.json` on disk changes nothing.

</Details>

</div>

<div className="tutorial-quiz">

**2. Why does `HYDRA_FORGE` have no default?**

<Details summary="Hint">

What does a script do with your token once it has decided which forge to talk to?

</Details>

<Details summary="Answer">

Guessing a forge means sending the run's credentials to a third party. It used to default to `codeberg`, and that is how a GitHub token once ended up at codeberg.org. Now the scripts refuse to start until you say `github` (every ConductionNL repo) or `forgejo` (a customer's self-hosted Forgejo).

</Details>

</div>

<div className="tutorial-quiz">

**3. Why call `./scripts/hydra-label.sh` instead of `gh issue edit --add-label` when triggering a run?**

<Details summary="Hint">

The labels are the source of truth, but there is a second thing that has to follow them.

</Details>

<Details summary="Answer">

`hydra-label.sh` goes through the label helpers in `scripts/lib/labels.sh`, and every one of those ends by syncing the GitHub Project board. So one call changes the label and moves the card. `gh issue edit` changes only the label; the board stays in the old column until `reconcile.sh` (every 10 minutes) catches the drift.

</Details>

</div>

<div className="tutorial-quiz">

**4. Your `smoke-test.sh` chain came back green. What have you proven, and what not?**

<Details summary="Hint">

What does a run leave behind when no flow is involved?

</Details>

<Details summary="Answer">

**Proven:** the builder, reviewer and security stages work on this spec, with these images and these credentials.

**Not proven:** anything about sequencing or attribution. `smoke-test.sh` and `dev-run.sh` start containers directly, so no `hydra.json` stage record is written, no owner is attributed, and no label state machine is exercised. Claims of the form "the stage records prove it" need a run through the flows.

</Details>

</div>
